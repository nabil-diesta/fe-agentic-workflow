How the Agentic Workflow Works

Niesta connects your Jira board to an AI pipeline that handles the full engineering process — from reading a ticket to writing code and generating a PR. OpenAI plans and documents; Codex CLI writes and tests the actual code. You stay in control with a mandatory approval gate before any code is touched.

Each pipeline runs as a background process. You can open, close, and revisit the pipeline view at any time — steps update in real time and the pipeline keeps running whether the dashboard is open or not.

The 9 Steps

Every pipeline runs the same 9 steps. Steps 1–5 are AI planning; step 6–7 are Codex coding; steps 8–9 are AI documentation.

1
Kickoff gpt-4o-mini Plain-English summary of what changes, why, and who is affected.
2
Scope gpt-4o-mini In scope, out of scope, and assumptions — the guardrails for the work.
3
Impact Map gpt-4o-mini Every component, service, route, and API contract affected by this change.
4
Risk Pass gpt-4o-mini Security, data integrity, performance, compliance, and regression risks — each rated LOW / MEDIUM / HIGH.
5
Test Plan gpt-4o-mini Jest unit tests, Playwright E2E tests, and regression targets. References your existing test structure.
—
Approval Gate Human Pipeline pauses here. Review, edit, or rerun any planning step before coding begins.
6
Implement Codex CLI Codex reads your codebase, applies changes within the agreed scope, and writes tests.
7
Validate Codex CLI Runs Jest unit tests and Playwright E2E tests. Reports results against the test plan.
8
Document gpt-4o-mini Jira comment, follow-up ticket suggestions, and notes for reviewers.
9
PR Prep gpt-4o-mini Complete PR title, structured markdown description, file change summary, and rollback plan.

The Approval Gate

After Step 5 completes, the pipeline pauses at the Approval Gate. No code is written until you click approve. The pipeline will wait indefinitely — come back in an hour, a day, or a week and it'll be right where you left it.

This is the human-in-the-loop checkpoint. Review the AI's plan carefully before approving. Once you approve, Codex starts making changes to your codebase.

What you can do before approving

  • Edit any step — click Edit on any completed step to open a textarea. Modify the output directly (it's markdown). Click Save. Your edits are used as context for Codex in Step 6.
  • Rerun a step — if a step's output is poor, click Rerun to regenerate it from scratch. The step re-fetches the ticket from Jira and runs fresh.
  • Skip a step — mark a step as skipped if it's not relevant (e.g., Risk Pass for a simple copy change). Skipped steps are excluded from the Codex context.

While Codex is Working

Steps 6 and 7 use the Codex CLI rather than the OpenAI API. Codex runs as a local subprocess, reads your actual codebase, and makes targeted changes.

  • Step 6 — Implement: Codex receives the full context from steps 1–5 as a structured prompt. It reads the files listed in the impact map, implements changes within the agreed scope, and writes or updates tests.
  • Step 7 — Validate: Codex resumes the same thread (no fresh context lost) and runs npm test (Jest) and npx playwright test if Playwright is configured. Results are reported against each item in the test plan.
  • Validation failures don't abort: If Step 7 fails, it's marked as failed but the pipeline continues to Steps 8–9. You still get the documentation and PR description.
  • You can check in: Go to Active Tasks to see the Codex task, then click "Check In" to view the full conversation thread in real time.
Steps 6 and 7 can take several minutes depending on the size of the change. The pipeline view polls every 3 seconds — no need to refresh.

What You Get at the End

Step 8 — Document
  • Jira comment ready to paste, summarising what was done
  • Follow-up ticket suggestions for deferred work
  • Notes for reviewers about decisions made during implementation
Step 9 — PR Prep
  • PR title in feat(DD-XXX): description format
  • Full markdown PR description: What, Why, How, Testing, Risks
  • File change summary with rationale per file
  • Rollback plan

The "Copy PR Description" button on Step 9 copies the full output to your clipboard. Paste it directly into your Bitbucket or GitHub PR.

Tips

  • Steps 1–5 take around 25 seconds total. Grab a coffee, then come back to review.
  • Edit step outputs to add context the AI missed — especially the Scope and Impact Map before approving.
  • Skip irrelevant steps (e.g. Risk Pass for a simple label change) to keep Codex context focused.
  • The pipeline view auto-polls every 3 seconds. No need to refresh.
  • Multiple pipelines can run simultaneously — one per ticket.
  • "Start Work" still exists on the ticket panel if you want Codex without the planning phase.
  • Completed pipelines are saved in the Pipelines history view for 30 days.
  • Kanban cards show a mini progress bar when an active pipeline exists for that ticket.
  • Cost is approximately $0.01–0.02 per pipeline (planning + doc steps via gpt-4o-mini).

For developers who want to understand the internals.

Services

  • Listener (port 4000): TypeScript + Fastify 5. Manages all Jira, Codex, and pipeline operations. Persists tasks and pipeline steps to SQLite (tasks.db).
  • Dashboard (port 4200): Angular 20, standalone components, signal-based reactivity. Polls the listener every 3–10 seconds depending on view.
  • VPS Agent (port 8000, optional): Python + FastAPI, runs on a remote VPS, handles Telegram bot interactions and can trigger Jira queries.

Codex App Server

The listener spawns a single persistent codex app-server subprocess on startup. Communication is via JSONL over stdio (a JSON-RPC-style protocol). Threads are started, resumed, and read via this subprocess. Each Codex task gets its own thread; Step 7 resumes the same thread as Step 6 so Codex has full implementation context when validating.

OpenAI usage

Steps 1–5 and 8–9 call OpenAI directly via fetch with gpt-4o-mini, temperature: 0, max_tokens: 1500. Each step builds on the output of previous steps as context. Total cost per pipeline: approximately $0.01–0.02.

Approval gate mechanism

After Step 5, the background async function parks on a Promise whose resolve is stored in a Map<taskId, fn>. The POST /pipeline/:taskId/approve endpoint calls that resolve function, unblocking the background process. The pipeline resumes from exactly where it stopped.
